# Architecture

`src/dogfood.py` is a single Python standard-library HTTP server. Every API request opens a short SQLite connection and closes it after commit or rollback. Next.js serves the React portal on port 3000 inside Compose and forwards `/dogfood-api/*` to the Python service. The Python service renders the public `/projects` gallery so fixture project titles appear in the initial HTML. SQLite data lives in the `portal_data` Compose volume. In development, Next.js forwards the same routes to the Python service on port 8000.

Authentication uses password hashes with PBKDF2-HMAC-SHA256 (250,000 iterations) and random salts. Sessions use random tokens; only SHA-256 token hashes are stored. Browser sessions use HttpOnly, SameSite=Strict cookies. Cookie-backed writes check the request origin. The published checker uses seeded bearer tokens. `DOGFOOD_DEMO_MODE=0` disables demo fixture/account creation on a new database.
For a fresh non-demo database, `DOGFOOD_ADMIN_EMAIL` and `DOGFOOD_ADMIN_PASSWORD` create the first platform admin. API event dates require an explicit timezone offset.

Authorization runs on the server. A visitor may browse events and submitted projects. A signed-in participant may create one team per event and edit only their team's project before the deadline. Judges see only assignments and review scores belonging to their user ID. Organizers manage roles, assignments, rubrics, progress, exports, and prepublication results for their event. Admins may manage every event. The current score endpoint checks the authenticated user ID against the URL even for admins, which limits accidental score disclosure.

The fixture importer uses stable source IDs and `INSERT OR IGNORE`, so repeated starts do not duplicate the 41 project records. `prj_41` is retained and flagged as a duplicate of `prj_07`; it is excluded from normalized score calculations. Separate open submission, pending review, and two-project community voting demos are seeded without changing the historical fixture event. The event lifecycle is open submission, judging, optional voting, then publication. Publication freezes a result snapshot.
Once published, rubric changes, new assignments, review edits, timing changes, and republication are rejected. CSV export reads the frozen snapshot.

Community ballots are returned only to signed-in accounts while the voting phase is open. The server shuffles each ballot with `SystemRandom`; votes have a unique event/user constraint and prevent team members choosing their own project. SQLite immediate write transactions serialize duplicate and rate checks before inserts. Community totals are visible to the organizer after the voting deadline and to everyone after publication. Submitted-project comments are public to read; posting requires an account, duplicate text and account rate limits are checked, and organizers can hide comments. Accepted and rejected abuse actions are recorded in `audit_events`. These controls reduce repeat activity from one account but do not establish that separate accounts belong to different people.

The REST API is described by `src/openapi.json`. Organizer JSON export is a full event archive with account references but excludes password hashes, sessions, and signing keys. Import is transactional and maps tracks, prizes, teams, projects, and matching existing team-member accounts into a new unpublished event; reviews, votes, comments, and roles are retained in the export but are not restored by import. Event activity queues webhook deliveries in SQLite. After a successful write the server POSTs JSON with an HMAC-SHA256 signature; pending deliveries are retried on later writes or explicitly by an organizer, with three attempts maximum. The delivery mechanism is synchronous and best-effort rather than a dedicated background worker.

Publishing an event issues immutable project certificates and judge participation records. Each record stores a canonical JSON payload and an HMAC-SHA256 signature made with a key held in the database. The public `/verify/{id}` and `/api/records/{id}` endpoints recalculate the signature and reject tampered URLs. Because verification depends on the running server's private key, it is not independently verifiable offline. The public `/embed/events/{id}` route renders a standalone submitted-project gallery for an iframe.

The React workspace and arcade are mounted through Next.js. `src/DogfoodWorkspace.jsx` adds event controls to Admin, submission forms to Contestant, assigned reviews to Jury, and community ballots/comments to the gallery. CSS provides a responsive visual system, card motion, and scroll cues; effects honor reduced-motion preferences. Tailwind is compiled locally. `src/localStore.js` persists browser-only dashboard panels with query and subscription behavior. Arcade scores are also browser-local. Shared DOGFOOD event data uses SQLite and backend authorization. Browser storage is a demonstration surface rather than a shared or role-secured event database; any browser-only workflow used for a real multi-user event would need a dedicated backend endpoint and authorization tests.
