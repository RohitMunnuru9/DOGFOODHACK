## Mission and evaluation

Build one self-hosted product for an entire hackathon lifecycle: registration, teams, submissions, eligibility, judge assignment, scoring, normalization, results, and export, with certificates and a queryable archive as later stages. A stranger must be able to start a seeded portal with `docker compose up` and no network access at runtime. The project must be more than static screens and must enforce roles and deadlines in the backend.

T1 is the judging gate: authentication and roles, events, teams, submission with deadline checks, and public gallery. T2 adds judge invitation and assignment, a weighted rubric, backend role isolation, progress, cross-judge normalization, and CSV export. T3 adds community voting, comments, results withheld until the voting window closes, randomized ballots, and an abuse audit trail. T4 adds documented REST API and webhooks, certificates, verifiable judge records, embeddable gallery, and bulk import/export. Correctness matters more than a high tier claim.

The published `run.py` has seven checks only: unauthenticated gallery returns 200, a fixture title appears, a closed fixture event rejects a participant's POST, judge A can read their own scores, judge B cannot read judge A's scores (401/403), a participant cannot read judge scores (401/403), and an organizer gets a CSV. `fixtures.json` contains 40 original projects plus an intentional duplicate row, 30 judges, eight tracks, scores, a constant-scoring judge, and unfinished review batches. Preserve the fixture's historical deadline. T3 and T4 are reviewed manually.

Scoring: tier completion/correctness 40%, judging integrity 25%, adoptability/operability 20%, code quality/innovation 15%. T1 must pass before scoring. The bonus challenges are a defensible normalization proof (+5 tie-break), Bradley–Terry pairwise judging (+5), a written abuse threat model (+3), and an API-first implementation with OpenAPI (+3). Bonus points break ties rather than changing the weighted score. A clear explanation of assignment and normalization in `JUDGING.md` matters directly to judging integrity.

## Required deliverables

- Public repository under an OSI-approved license, preferably MIT or Apache-2.0, with rights to every included file.
- `docker-compose.yml` for a seeded offline runtime; root `.dogfood.toml` with honest tier claims and working role headers/routes; `acceptance-report.txt` generated by the published checker and committed even if it has failures.
- `README.md`, `ARCHITECTURE.md`, `DATA-MODEL.md`, and `JUDGING.md` explaining use, design, schema/import/export, assignments, scoring, and normalization.
- A five-minute video showing one complete event lifecycle.

Use the postponed build deadline above for submission planning. The fixture event's March deadline is historical test data and must stay unchanged. Organizer registration, final submission and any write-up are separate actions by the entrant.

The winner retains ownership; organizers say they will fork and self-host the project, credit it on event pages, and send changes back as pull requests. The write-up should explain concrete design choices, bugs, tradeoffs, and things cut or learned; insight matters more than audience size.

## Exclusions and this repository

The brief excludes a hardcoded frontend or mockup, cloud-dependent startup, a login-only demo, gallery without judging or vice versa, frontend-only role checks, undocumented generated code, closed or unlicensed code, and a renamed rewrite of an existing platform. Planning, frameworks, libraries, and AI tools were allowed before kickoff, but project code had to begin in the event window.

The repository is MIT licensed. Its submitted interface uses explicit account sessions and shared backend workflows. Track-scoped balanced assignments, organizer questions, full-history archive restoration, configurable voter invitations, safe public stories, frozen public results, OpenAPI validation and reproducible normalization evidence have been added. Docker, isolated runtime, browser lifecycle, authorization and abuse checks are described in `TESTING.md`. `.dogfood.toml` claims T1–T4. The published checker certifies seven T1/T2 probes only; `TIER-EVIDENCE.md` maps the T3/T4 requirements to code and separate tests without presenting them as host-verified.

Submission still requires the entrant to provide the repository and demo link to the organizers and confirm any team, authorship, asset-rights and build-window declarations. The code and tests cannot certify those personal facts. See `DEMO.md` for the lifecycle walkthrough.
